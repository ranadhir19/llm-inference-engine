Serving at Scale

Scheduling Lab

Continuous batching vs chunked prefill vs preemption: a scheduling shootout

1The problem

How a serving engine schedules requests across GPU iterations decides the latency every user feels. A single 4k-token prompt prefetched in one iteration stalls every in-flight decode; a fixed batch that runs to completion head-of-line-blocks everything behind it; and under KV-cache pressure, someone has to decide which request loses its slot. These tradeoffs are usually argued from intuition. sched-lab measures them.

2The current gap

Most scheduling discussions compare policies qualitatively ("continuous batching is better") or on production systems where the workload, the hardware, and the scheduler change at once. There was no small, reproducible harness that isolates the scheduling policy — same seeded workload, same analytical GPU cost model, same KV budget — and reports TTFT/TBOT tails, throughput, and utilization per policy.

3How the solution addresses it

src/llm_inference_engine/sched_lab/sim.py implements an iteration-stepped discrete-event simulator behind one Scheduler interface:

  • static-fcfs — fixed FCFS batches run to completion; if the queue head does not fit the KV budget, nothing behind it is admitted (genuine head-of-line blocking).
  • continuous — vLLM-style iteration-level batching: waiting requests join freed KV slots every iteration; a full prompt prefetches in one iteration.
  • chunked-prefill — Sarathi-style: each prompt is processed in 512-token chunks interleaved with decode steps, bounding per-iteration latency.
  • priority-preempt — short requests are admitted ahead of long ones and preempt them under KV pressure. A preempted request loses its KV cache and must recompute prompt_len + generated_so_far tokens on rescheduling — the recompute cost is charged honestly as extra batch tokens in later iterations, and counted in the metrics.

GPU model: each iteration costs t = T0 + K * batch_tokens (T0 = 2.0 ms, K = 0.012 ms/token). KV cache is a hard 16384-token budget; each admitted request reserves prompt_len + gen_len up front. Workloads are Poisson arrivals with a mixed shape (chat prompts 32–512 tokens, document prompts 1024–4096). Everything is seeded (np.random.default_rng(61)); three consecutive runs produce byte-identical headlines, results.md, and charts.png.

6Insights

  • Iteration-level admission is the dominant win. Moving from run-to-completion batches to per-iteration admission cuts high-load TTFT p99 by 42x. Everything else is second-order.
  • Chunking bounds the worst iteration, not the average wait. A synchronized long-prompt burst creates one giant iteration under continuous batching (concentrated pain: few requests hurt badly) versus many bounded iterations under chunking (spread pain: more requests hurt mildly). At p99 the two can tie; the win shows up in worst-case iteration latency (82.8% lower) and in TBT stability for decodes already in flight.
  • Preemption is a latency redistribution, priced in recompute. 4.88% extra compute bought an 87.9% short-request p99 improvement here — a good trade when short requests are the product, but the preempted longs pay the full recompute of prompt plus generated tokens.
  • KV pressure, not iteration cost, is the cliff. As long as every policy sustains the offered token rate, throughput is policy-independent; latency diverges only when queueing starts. Size the KV budget for the burst, not the average.
