Agent Governance

Remit Drift

Divergence of remit in multi-agent systems: measured per type, governed by a policy engine

1The problem

Agentic systems learn, plan, call tools, delegate, spawn subagents, and optimize objectives. Each mechanism can quietly expand behavior beyond the intended mandate: a calendar agent that starts sending email, an expense agent that starts approving instead of recommending, a support agent that discovers the fastest way to cut response time is closing every ticket. Nobody redesigns these agents — the remit drifts. When it does, nobody can answer "who authorized this agent to do that?", and the failure surfaces as a compliance incident, not a metric.

2The current gap

Remit drift is discussed qualitatively (blog posts, incident reports) but rarely measured. There was no small, reproducible harness that (a) defines the eight divergence types precisely enough to compute, (b) lets drift emerge from plausible mechanisms over time, and (c) tests which governance control actually catches which type — instead of asserting that "policy engines" fix everything.

3How the solution addresses it

src/llm_inference_engine/remit_drift/ implements:

  • Remit as a first-class object (remit.py): purpose, responsibilities, per-task authority levels (read/recommend/modify/admin), named plan constraints, proxy vs true success criteria, tool and data allow-lists, delegation caps, and temporary grants with TTLs.
  • D(t) metrics (metrics.py): one measure per divergence type — functional drift as KL between the task distribution and the remit profile; authority/tool/information/planning as violation rates; goal divergence as the proxy-vs-true objective gap; collaboration as excess delegation; temporal as expired-grant usage.
  • Policy engine (policy.py): validates every planned action — allow/deny/escalate — with nine independently switchable controls (explicit remit, capability registry, policy engine, tool allow-lists, authorization checks, planner constraints, continuous auditing, human approval, remit versioning).
  • Drift simulator (sim.py): agents over discrete time steps where drift emerges from request pressure (p_out(t) = 1 - e^(-t/tau)), privilege creep, tool/data boundary creep, plan decay, delegation drift, grant decay, and normalization of deviance — repeatedly denied out-of-remit requests being silently absorbed into the agent's self-view of its remit unless versioning blocks it.
  • Scenarios (scenarios.py): eight single-mechanism specialists, the enterprise finance agent (invoice reader → creates vendors, edits suppliers, changes bank details), and the support-ticket goal-divergence demo (epsilon-greedy bandit learns that closing tickets immediately optimizes response time while satisfaction collapses).

6Insights

  • A written remit the agent self-enforces is not enough. In the simulation, repeated denied out-of-remit requests are silently absorbed into the agent's self-view after ~25 attempts (normalization of deviance), so explicit_remit alone does not contain functional drift. Central enforcement (capability registry / policy engine) plus remit_versioning is what holds the boundary. This is the defense-in-depth argument, measured.
  • Authorization is the quiet backstop. auth_checks catches functional, authority, goal, and temporal drift, because out-of-remit actions inherently lack a grant — attempting authority ≥1 with no grant is denied. Least privilege is doing more work here than the fancier controls.
  • Detect-only still matters. auditing flags 7 of 8 types (everything except pure delegation drift, which needs a cap, not a detector) — it cannot block, but it is the only control that sees goal divergence *as it happens*, before the metric collapses.
  • Sophistication is not the defense; the boring controls are. Tool allow-lists, grant TTLs, and delegation caps each contain exactly their vector, completely. The exotic failure (scope drift) yields to the unglamorous checklist.
  • Remit belongs in the runtime, not the prompt. Validating every planned action against a declared, versioned remit before execution — rejecting, escalating, or routing — is what turns divergence from a post-incident discovery into a measurable, controllable quantity.
