Serving at Scale

LLM Mesh

Many specialized models, one routing layer: route, orchestrate, aggregate

1The problem

One frontier model for every request is the most expensive way to serve mixed workloads: you pay frontier prices for chit-chat, wait on a reasoning model's latency for a simple summary, and you inherit a single vendor's outage as your own. In practice, different models are best at different tasks, but there was no small reproducible harness that quantifies what a mesh buys you: how much cost routing saves, what parallel fan-out is worth, whether a router can learn the mapping on its own, and what happens when a specialist goes down mid-shift.

2The current gap

Mesh discussions are usually architectural diagrams: boxes labeled "router" and "orchestrator" with no numbers attached. The questions that decide whether a mesh is worth building — quality vs cost vs latency tradeoffs per routing policy, the learning curve of an adaptive router, the blast radius of a model outage with and without failover — were argued qualitatively. llm-mesh simulates five specialized models with analytical quality/latency/cost profiles and measures the mesh machinery against a single-model baseline on identical seeded workloads.

3How the solution addresses it

src/llm_inference_engine/llm_mesh/ implements the mesh components:

  • Model registry (models.py) — five simulated specialists (frontier-1, reasoner-r1, coder-cl, vision-qw, general-8b), each with per-task quality means, per-token latency, and per-token price. Calls are sampled with seeded noise; no real LLM is invoked.
  • Semantic router (router.py) — TF-IDF + class-centroid (Rocchio) classifier mapping raw queries to reasoning / coding / vision / chat, plus four routing policies: quality-first, cost-first, latency-first, balanced.
  • Orchestrator (orchestrator.py) — decomposes a request into typed subtasks, dispatches sequentially or in parallel (wall-clock modeled as max latency + aggregation overhead), aggregates results, and fails over to the next-best model on ModelDown. Tool agents (e.g. a fraud-DB check) are simulated as fixed-latency stages.
  • Self-improving router (bandit.py) — one UCB1 bandit per task type learning the best model from scored outcomes, plus a DynamicSelector that scores models from rolling observed quality/cost/latency means.
  • Observability (observability.py) — append-only Trace of every invocation: routing decision, model, latency, tokens, cost, quality, failover provenance.
  • Workflows (workflows.py) — the two canonical pipelines from the concept: fraud-risk insurance claims (vision extract -> reasoning -> tool DB check -> summary) and chart+report explanation (parallel vision + chat fan-out, reasoning combine).

6Insights

  • Specialization beats scale on cost, and slightly on quality. Routing each task to its best model cut cost 62% while raising mean quality 2.8 points versus the frontier-only baseline. The mesh tax is paid in tail latency when the best-quality model is also the slowest.
  • Parallelism is the cheapest latency win in the mesh. 1.64x on a two-way fan-out with a 50 ms aggregation overhead — independent subtasks should never run sequentially.
  • Adaptive routing converges without prior knowledge. The UCB1 router, starting from zero knowledge of the quality profiles, cut regret 5x over 3000 requests. Small oracle gaps plus reward noise mean it keeps exploring — tune the exploration constant if you want faster lock-in.
  • Failover is the mesh's reliability story. A single-model outage is a 25% outage for static routing and a non-event for the mesh. The registry's health check is load-bearing infrastructure, not a nicety.
  • Policy is a business decision, not a technical one. The Pareto front is real: quality-first costs 5.8x cost-first. Balanced sits in a genuinely useful middle ($0.43, 0.847).
