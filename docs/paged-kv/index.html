Serving at Scale

Paged KV-Cache

vLLM-style paged block manager: quantifying fragmentation waste vs contiguous allocation

1The problem

During autoregressive decoding, each sequence's KV cache grows token by token, but its final length is unknown at admission. A serving system must reserve GPU memory per sequence without knowing how much each will need.

2The current gap

The naive approach reserves the worst case (max_len = 2048 slots) as one contiguous run per sequence, placed with first-fit. Two costs follow:

  1. Internal fragmentation: a 128-token sequence sits in a 2048-slot reservation; the unused slots are stranded until the sequence finishes.
  2. Wasted capacity: those stranded slots cannot serve other sequences, so the server sustains far fewer concurrent requests than the memory could physically hold.

3How the solution addresses it

src/llm_inference_engine/paged_kv/ implements:

  • blocks.py — BlockManager: the pool is split into fixed-size blocks (B tokens each); a sequence of n tokens takes ceil(n / B) blocks from a free list, recorded in a per-sequence block table. Blocks are fungible, so any free block serves any sequence. Plus ContiguousAllocator: the naive baseline, reserving max_len contiguous slots per sequence with first-fit placement and interval coalescing on free. Both expose identical accounting (used_slots, allocated_slots, total_slots, fragmentation).
  • workload.py — gen_workload: 2000 requests; lengths from a 70/20/10 mixture of N(128,32) / N(512,128) / N(2048,256), clipped to [1, 2048] (measured mean 373 tokens); arrivals uniform over 600 time steps; each sequence completes length steps after arrival.
  • experiments/run_experiments.py — event-driven arrival/departure simulation through both allocators (seed np.random.default_rng(11)), the B sweep, charts, and results/results.md. The pipeline runs twice and asserts identical headline numbers before writing anything.

6Insights

  • Paging converts a capacity problem into a rounding problem. The contiguous baseline strands 2048 - length slots per sequence; paging strands only the unused tail of the last block (at most B - 1 slots). At B=16 that is 1.90% waste instead of 81.51%.
  • Waste is throughput. The paged allocator admits all 2000 requests and peaks at 817 concurrent sequences; the contiguous allocator hard-caps at 488 (1M / 2048) and rejects 603 requests — a 1.67x concurrency gap from memory management alone, with identical hardware.
  • **Block size trades waste against table overhead, but the table is cheap in bytes.** Halving B roughly halves waste (7.50% at B=64 down to 0.87% at B=8) while doubling the block table — yet even at B=8 the table is 1 MB against ~524 GB of KV memory (32 layers x 4096 hidden x fp16). In practice the small-block cost is kernel and bookkeeping complexity, not bytes; B=16 is the usual sweet spot.
  • No external fragmentation was observed for either allocator in this workload: paged blocks are fungible by construction, and the baseline's uniform 2048-slot reservations mean every freed interval is itself a valid placement. The baseline's 603 rejections are pure internal fragmentation — memory that is free but reserved for sequences that will never use it.
